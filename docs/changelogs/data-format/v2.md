# Data format v2

## What changed from v1

### Sidecar files for long text values

When a JSON string value contains more than one CommonMark content block
(paragraph, heading, list item, code block, or blockquote), the pipeline
automatically **promotes** it to a sidecar: a standalone `.md` file at
`<stem>.sidecars/<json-pointer-segments>.md`. The JSON field value is replaced
with a wikilink pointing at the sidecar.

Example: a `"Notes"` field in `Garden.json` with two paragraphs becomes
`[[Garden.sidecars/Notes.md]]`, and the markdown lives in that sidecar file.

Single-block values (one paragraph, one heading, etc.) are stored inline in
the JSON as before.

The pipeline propagates sidecar files automatically on restructuring:
- **Rename `Garden.json` → `Park.json`** → sidecar directory renamed to `Park.sidecars/`; wikilinks rewritten.
- **Delete `Garden.json`** → `Garden.sidecars/` deleted entirely.
- **RFC 6902 `move` op on a field** → sidecar file/subtree moved to match the new path.
- **RFC 6902 `remove` op on a field** → sidecar file/subtree deleted.

The bot must never create sidecar files directly or construct sidecar wikilinks
by hand — the pipeline does it automatically on `json_patch add/replace`.

### New structural invariants (enforced at end of every `apply`)

- **Index integrity:** `Index.json` must be a valid array; each entry must have
  a non-empty `File` (wikilink form `[[path]]`) and a non-empty `Scope`. No
  duplicate `File` values. Every non-dot-prefixed file must have an index entry.
- **No stem/directory collision:** a file `Foo.json` and a directory `Foo/` may
  not coexist in the same parent. (`Foo.sidecars/` is not a collision.)
- **Wikilink integrity:** every `[[path]]` in every file must resolve to an
  existing file in the repo.
- **Sidecar integrity:**
  - Every `.sidecars/` directory requires its owner `.json` file to exist.
  - `.sidecars/` directories contain only `.md` files.
  - Each sidecar `.md` is referenced by exactly one JSON field (the owning field value).

## Migration: v1 → v2

Run the `/<assistant>-migrate` skill, which drives the bot through
`jadelens/migrations/v1_v2/RUNBOOK.md`:

1. **Batch-promote inline strings:** calls
   `jadelens run-migration-helper <repo> v1_v2/promote-sidecars`, which scans
   every JSON file and promotes qualifying multi-block string values via
   `jadelens apply --unsafe`.
2. **Resolve stem/directory collisions:** bot checks for and renames any
   colliding paths (asking the user if intent is unclear).
3. **Final integrity check:** `jadelens check <repo>` confirms all v2
   invariants pass before the migration is sealed.
